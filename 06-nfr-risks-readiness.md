# 06. Нефункциональные требования, риски, готовность

## 6.1 Нефункциональные требования

| ID | Требование | Как проверить |
|----|------------|---------------|
| NFR-1 | Повторный прогон с новым ключом идемпотентности даёт тот же метод и расхождение по треугольникам не больше 15% | Сравнение двух отчётов |
| NFR-2 | Код и комментарии на английском | Ревью |
| NFR-3 | Секреты не хранятся в репозитории и не попадают в образ контейнера; в тестовом наборе нет лиц крупным планом | Проверка в CI и просмотр эталонных бандлов |
| NFR-4 | Успешная сборка не зависит от установленного игрового движка | Ходьба в браузере |
| NFR-5 | Параметры прогона задаются конфигом и воспроизводятся | Повторный прогон с тем же конфигом |
| NFR-6 | Приложение доступно по публичному адресу и разворачивается из контейнера | Открытие по ссылке и подъём среды по описанию в Terraform |

## 6.2 Риски

| Риск | Влияние | Что делается |
|------|---------|--------------|
| Меш получается неузнаваемым | Высокое | Небольшая зона съёмки, обязательные позы, отказ вместо произвольной геометрии |
| У проверяющего нет телефона с LiDAR | Высокое | Сохранённые эталонные бандлы, сценарий проходится через браузер |
| Обработка требует много ресурсов | Среднее | Настраиваемый размер зоны, ограничение числа кадров и точек |
| Съёмка не проходит проверку | Среднее | Причина отказа формулируется на экране и в отчёте, оператор переснимает зону |
| Геометрию случайно масштабируют | Высокое | Масштаб не меняется, в манифесте фиксируется только центрирование |
| Загрузка оборвалась, задание без статуса | Среднее | Повтор с тем же ключом идемпотентности возвращает текущее задание |

## 6.3 Зависимости

| Зависимость | Зачем |
|-------------|-------|
| iPhone или iPad Pro с LiDAR | Съёмка в основном режиме |
| Хостинг-провайдер | Публичный адрес, PostgreSQL, хранилище файлов, секреты |
| Эталонные бандлы | Проверка без телефона и повторяемость |
| Образ с пайплайном реконструкции | Сборка карты в контейнере |

## 6.4 Данные и персональные данные

- Снимается участок пола, стола или макета, без лиц крупным планом.
- В базе лежат съёмки, задания, метрики и ссылки на файлы; сами файлы — в хранилище.
- Пароли от базы и хранилища задаёт хостинг, в образ они не попадают.
- Доступ к приёму бандла и выдаче пакета — по ключу; пользовательских аккаунтов на старте нет.

## 6.5 Готовность к приёмке

Пакет бизнес-анализа готов, когда в нём есть: проблема и цель, стейкхолдеры, границы, допущения, сценарии по шагам, схемы экранов съёмки и браузера, стиль, персоны, проверка понимания зоны и обхода, user stories с критериями приёмки, приоритеты, нефункциональные требования, риски и согласованное ТЗ.

Продукт готов к релизу, когда:

1. Оператор понимает зону, обход и момент, когда запись пригодна.
2. Пригодные эталонные бандлы собираются, непригодные получают отказ с причиной.
3. Карта лёгкая: укладывается в бюджеты треугольников и размера файлов.
4. Сборщик проходит по коллизии в браузере по публичному адресу, рядом виден исходный кадр.
5. Разработчик игры получает пакет в размерах датчика, геометрия не масштабировалась.
6. Повторный прогон даёт тот же метод и близкое число треугольников.

Релиз не принимается, если успех получен подстановкой заглушки, карта доводится вручную после пайплайна, пайплайн масштабирует геометрию, персонаж проваливается сквозь коллизию или непригодный вход завершился успехом.

Числовые пороги, тестовые случаи и контракт API — в [ТЗ](../diplom-docs-2026-09-27/explain/tz-sistema-igrovyh-3d-kart.md).
