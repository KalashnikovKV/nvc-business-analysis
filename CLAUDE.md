# Бизнес-анализ NVC Maps

Блок бизнес-анализа по требованиям 2026/27: введение, глава 1, глава 2, литература, приложения 1 и B, заявления. Требования к блоку — `../diplom-docs-2026-09-27/1_Business Analysis Block Requirements…pdf`. Правила — `BA-METHOD.md`, оглавление — `README.md`.

## Структура

- `00`–`06-*.md` — русские разделы; `en/00`–`en/06-*.md` — английский перевод с теми же ключами источников. Правка смысла — в обоих языках.
- Сдаётся английский `wireframes/BA_Kalashnikov_Kirill.docx` (и `.pdf`); русская копия — `BA_Kalashnikov_Kirill_RU.docx` и `NVC-Maps-бизнес-анализ.pdf`. Подписи в английском: «Table N.M.», «Image N.M.», «Appendix N», «Table A.1.1», «Image A.2.1».
- `04-appendix-a-backlog.md` и `NVC-Maps-бизнес-анализ.md` генерируются — правки только в разделах.
- `scripts/slides.py` — презентация для защиты: описание слайдов данными; из него собираются `wireframes/deck.html` и PowerPoint `wireframes/NVC-Maps-защита.pptx` (`scripts/build-pptx.mjs`). Состав: титул и 8 слайдов доклада. Ответы на вопросы комиссии и материалы после доклада — только на странице `wireframes/prep.html`, в показ не входят. Правила: одна мысль, до 30 слов, ссылка на раздел внизу, без цепочки-трекера над слайдами, без сокращений и идентификаторов (никаких KPI, NFR, US-4.1, «мин», «ст.»). Цифры — из разделов 00–02, при их правке обновлять и слайды.
- `wireframes/` — сайт (GitHub Pages): `d0X-*.html` генерируются из разделов, `m*`/`b*` — макеты экранов, `shots/` — скриншоты макетов, `BA_Kalashnikov_Kirill.docx` и PDF — для скачивания.

## Команды

```bash
python3 scripts/build-ba.py          # бэклог, сводный файл, сайт, DOCX и PDF
python3 scripts/build-ba.py shots    # скриншоты макетов после правки m*/b*
npx markdownlint "**/*.md" --ignore node_modules --config .markdownlint.json   # как в CI
```

## Правила

- Пишем про продукт, а не про диплом: научный руководитель и комиссия — не стейкхолдеры.
- Админки в релизе нет — решение владельца продукта, не добавлять.
- Истории в 2.5 — строки таблиц `| US-x.y | … | … | Must |` под заголовками `### Ex.`; генератор бэклога читает именно этот формат.
- Источники — в `references.json` (описание по IEEE). В тексте ссылка `[@ключ]` или `[@a; @b]`; номера [n] по первому упоминанию ставит сборка; `03-references.md` генерируется, вручную не править.
- Новые обязательные файлы добавлять в список проверки в `.github/workflows/ci.yml`.
- Оформление DOCX — по «Правилам оформления письменных работ ЕГУ» (`../diplom-docs-2026-09-27/Rules for students papers_2025_final_RUS.pdf`): TNR 12, интервал 1,5, поля 25/10/20/20 мм, текст по ширине, заголовки разделов прописными по центру, номер страницы справа вверху. Главы — «1. АНАЛИТИЧЕСКАЯ ЧАСТЬ» без слова «Глава». Исключение по требованию эксперта блока БА: ссылки IEEE [n] вместо сносок Chicago. Приложения нумеруются цифрами («ПРИЛОЖЕНИЕ 1» в правом верхнем углу), рисунки и таблицы в них — «Рис. П.2.1», «Табл. П.1.1».
- У каждой Must-истории — позитивный и негативный критерий «Дано / Когда / Тогда»; пороги и тексты сообщений — как в коде приложения и сборки (табл. 2.10 — причины отказа).
- Термины — как в глоссарии введения: съёмка, видимая модель, опора, задание, эталонная съёмка; на макетах те же слова.
- Широкую таблицу (больше 7 колонок) обрамлять `<!-- landscape -->` … `<!-- /landscape -->` — в DOCX она уйдёт на альбомную страницу.
- Каждое утверждение с фактом или числом из внешнего мира — со ссылкой; там, где источник молчит, писать «не заявлено», а не «нет».
- Каждой таблице в разделах — подпись `Табл. N.M. Название` строкой перед таблицей и ссылка «(табл. N.M)» в тексте; рисункам — подпись «Рис.» под рисунком.
- После сборки смотреть `.build/docx-preview.pdf` глазами.
- Не читать `node_modules/`, `.build/` и PDF/DOCX без необходимости.
